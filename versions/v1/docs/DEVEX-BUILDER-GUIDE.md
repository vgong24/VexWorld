# Devex builder guide

## Mission

Use VexWorld as a source-grounded school: understand why a visible behavior exists, implement the smallest bounded change, prove it, inhabit it, critique it, and return a reusable lesson without silently promoting yourself or mutating unrelated architecture.

## Question route

```text
What experience should change?
→ which semantic capability owns it?
→ which source represents that meaning?
→ which scenario proves it?
→ which adapter realizes it?
→ which evidence closes it?
```

## Before coding

Answer:

```text
What meaning am I changing?
What source owns it?
What am I explicitly not changing?
Which participants are affected?
Which reality/effect class applies?
What assumption might be wrong?
What would invalidate my design?
```

## After coding

Run tests, then play or simulate. Classify surprises:

```text
IMPLEMENTATION_BUG
SOURCE_CONTRACT_BUG
SCENARIO_GAP
EXPRESSION_OR_UX_PROBLEM
BALANCE_PROBLEM
CONTROLLER_PROBLEM
NETWORK_OR_PERSISTENCE_PROBLEM
ARCHITECTURE_CONTRADICTION
NEW_POSSIBILITY
UNKNOWN
```

Repair the owning layer rather than patching symptoms everywhere.

## Early practicums

1. Change a tree expression without changing tree identity or collision behavior.
2. Add a new status input binding without renaming the status action.
3. Add a weather condition and prove resource-margin recalculation headlessly.
4. Add a companion controller without giving it direct world mutation.
5. Add a new team-technique signal projection while preserving decline/abort.
6. Add a World Witness pattern without using hidden relationship scoring.
7. Translate one ability into a second dimensional expression.
8. Create a reality-grounded Practice Twin while preserving uncertainty and physical-authority limits.
